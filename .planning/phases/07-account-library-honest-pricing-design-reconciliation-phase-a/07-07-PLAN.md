<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> /api/pass/intent, /api/pass/verify | PassModal only initiates; the routes enforce auth + PI ownership (07-03) |
| pass status read -> chip | Active/expired state derives from an RLS-scoped getActivePass row |
| Stripe Payment Element -> client | Card data handled by Stripe, never touches the app server |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-07-01 | Spoofing | PassModal purchase without auth | mitigate | /api/pass/intent returns 401 without a session (07-03); the modal is env-gated and only shown to signed-in users |
| T-07-07-02 | Repudiation | unclear withdrawal terms | mitigate | The distinct proportional §356(4)/§357a Widerruf consent gates submit and is flagged for legal review; "Endet automatisch / never renews" stated as fact |
| T-07-07-03 | Information disclosure | pass status of another user | mitigate | Chip status comes from getActivePass under RLS select-own; only the caller's pass is readable |
| T-07-07-04 | Tampering | Stripe card handling | mitigate | Card entry is the Stripe Payment Element; the app never sees raw PAN; verify runs server-side (07-03) |
| T-07-07-05 | Elevation of privilege | env-unset surfaces active | mitigate | accountsEnabled()/Stripe-config guards keep the modal + chip inert when keys are unset (Stage 3 pattern) |
</threat_model>
