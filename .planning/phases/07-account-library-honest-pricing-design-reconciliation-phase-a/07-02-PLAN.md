<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app/service-role -> Postgres | The enforce_package_limit trigger is the only storage-limit enforcement point |
| authenticated client -> humanizer_purchases (select) | RLS select-own scopes pass/purchase reads to the owner |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-02-01 | Tampering | enforce_package_limit() concurrency | mitigate | Keep `pg_advisory_xact_lock` as the first statement so concurrent inserts cannot bypass the tier count (verified by grep + the advisor) |
| T-07-02-02 | Elevation of privilege | pass_30d row without owner | mitigate | Check constraint `kind <> 'pass_30d' or user_id is not null` forces every Pass row to carry an owner; RLS select-own then binds reads to that owner |
| T-07-02-03 | Elevation of privilege | any new security-definer RPC | mitigate | No new callable RPC added; if one is added it gets the 0001 revoke-all + narrow grant-execute hardening; advisor re-run confirms no cross-user vector |
| T-07-02-04 | Information disclosure | listPaketPurchases / getActivePass reads | mitigate | Both go through the authenticated client under RLS select-own; a user can only read their own purchase rows |
| T-07-02-05 | Tampering | live schema drift vs repo | mitigate | Task 2 [BLOCKING] applies the migration and runs advisors, or records an explicit founder gate, so the live DB matches the repo migration before Pass routes are verified |
</threat_model>
