<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AI/user content → browser DOM | The finished letter (AI-generated, then user-edited) is rendered into a controlled `<textarea>` and a static callout. |
| browser → user filesystem | The `.txt` download writes user-held letter content to disk via a browser-native Blob — no server involvement. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-05 | Tampering (XSS) | Post-stream letter render + trust callout | mitigate | Letter renders as the `value` of a controlled `<textarea>` (text, never HTML); the trust callout is static `<p>` copy. No `dangerouslySetInnerHTML` (asserted by negative grep in Task 1). |
| T-02-06 | Information disclosure | `.txt` download + clipboard | accept | The Blob and clipboard write happen entirely client-side on content the user already holds; no new network egress, no server persistence. Consistent with zero-retention. Low risk. |
| T-02-07 | Information disclosure | `letterText`, `jobPosting`, `answers` in client memory | accept | Cleared by `RESET` ("Start over"); no `localStorage`/`sessionStorage`; no server-side logging introduced. Low risk. |
| T-02-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages — `.txt` download is browser-native `Blob`/`URL.createObjectURL`; copy is `navigator.clipboard`. No legitimacy checkpoint needed. |

Severity note: `security_block_on: high`. No high-severity unmitigated threat remains — the only Tampering vector (T-02-05) is mitigated by React's default text escaping and the no-`dangerouslySetInnerHTML` invariant.
</threat_model>
