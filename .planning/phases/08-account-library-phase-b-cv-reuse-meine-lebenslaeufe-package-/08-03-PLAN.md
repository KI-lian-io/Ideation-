<objective>
Deliver surface 07's "Meine Lebenslaeufe" section on /konto: the account holder can see each stored CV, how many applications use it, rename it, delete it (packages keep their own copy), and start a fresh application from it.

</objective>

## Phase Goal (user story)

**As a** signed-in job seeker, **I want to** see and manage my saved CVs on /konto and start a new application from one, **so that** I can reuse and clean up my CVs without ever losing the applications built from them. (Derived from PRD 6.4 and the 07 design deck; delete is "safe by design" because packages snapshot their own Lebenslauf.)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser client -> cvs read/update/delete | CV id from the card is used in RLS-scoped reads/writes |
| ?cv= param -> tool input | A client-supplied cv id is fetched and its text prefilled into the input |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-10 | Information Disclosure | ?cv= bridge / CV cards | mitigate | All cvs reads go through the RLS-scoped browser client (cvs_select_own); a foreign cv id returns null, so no other user's CV text can be loaded or listed. |
| T-08-11 | Tampering | CV delete | mitigate | Delete uses cvs_delete_own (owner-scoped) and never issues an application_packages write; the DB FK ON DELETE SET NULL (0004) nulls the reference so packages persist. A cross-user delete silently no-ops via RLS. |
| T-08-12 | Tampering | CV rename | mitigate | updateCvTitle writes only cvs.title under cvs_update_own; no other column and no other user's row is reachable. |
</threat_model>
