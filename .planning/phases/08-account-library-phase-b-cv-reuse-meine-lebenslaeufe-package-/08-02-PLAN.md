## Phase Goal (user story)

**As a** signed-in job seeker applying to many roles with one CV, **I want to** attach each new application to my existing Lebenslauf instead of duplicating the CV every time, **so that** my account holds one CV used across many applications rather than a pile of identical copies. (Derived from PRD section 5 / 6.4; the save card preselects attach when the CV clearly matches.)

## Trust Boundaries

| Boundary | Description |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-06 | Spoofing/IDOR | attach path existingCvId | mitigate | The UI only ever offers CVs returned by `listCvs`, which is RLS-scoped (cvs_select_own) to the signed-in user, so the picker cannot present another user's CV. |
| T-08-07 | Information Disclosure | referencing a foreign cv_id | accept | Even if a crafted client passed a foreign cv_id, `cvs_select_own` blocks reading that row (handleLoadPackage's cvs query returns null), so no CV text of another user is ever exposed; the package insert itself is still RLS-guarded by `auth.uid() = user_id`. |
| T-08-08 | Tampering | orphan-cleanup on attach branch | mitigate | The best-effort cvs delete runs ONLY in the save-as-new branch; the attach branch never deletes the reused (pre-existing) cvs row, so a limit error cannot destroy a CV shared by other packages. |
| T-08-09 | Denial of Service | null cv_id after a CV delete | mitigate | handleLoadPackage/handleDuplicatePackage guard the null cv_id and fall back to empty text; the package renders from its own snapshot, so a deleted CV cannot crash the load path. |
</threat_model>
